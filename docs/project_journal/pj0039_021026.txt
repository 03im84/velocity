Problema:

CompositionPlan describe:

- qué construir;

- qué factories resolver;

- qué dependencias declarar;

- qué comunicación enlazar;

- qué Dispatch Policy aplicar;

- qué órdenes de lifecycle usar.

Plan no ejecuta.

Falta un owner runtime que:

- cree DeviceBus;

- resuelva Dependency Values;

- construya Requests;

- invoque factories;

- conserve Handles;

- adjunte Host Objects;

- enlace comunicación;

- coordine lifecycle;

- haga rollback;

- ejecute shutdown;

- conserve estado observable.

Límites detectados:

1. Primary Runtime Object es Object.

No existe garantía de que sea Device
o que exponga lifecycle directamente.

2. Device.initialize() no recibe DeviceBus.

La entrega de Bus necesita adapter explícito.

3. Connection Directive no contiene callback.

Runtime necesita binder explícito.

4. Dependency Spec no contiene Value.

Runtime necesita resolver explícito.

5. Plan no contiene Registry.

Runtime recibe Registry aparte.

6. Hot swap no está diseñado.

Construir candidato mientras otro runtime
permanece activo puede provocar conflictos
de host, hardware o dependencies TRANSFERRED.

7. Hardware continúa bloqueado.

No existe evidencia safety completa
para activar hardware.

Decisión principal:

CompositionRuntime 1.0 será:

- Simulation-only;

- stateful;

- owner de recursos;

- one-shot;

- transaccional;

- sin hot swap;

- sin singleton;

- sin service locator.

One-shot significa:

Una instancia puede realizar
una activación candidata.

Después queda:

ACTIVE

SHUTDOWN

o

FAILED

No se reutiliza para otro Plan.

Last Known Good:

No pertenece a una instancia one-shot.

Pertenecerá a un Supervisor futuro.

Modelo futuro:

Active Runtime A

+

Candidate Runtime B

↓ B activa completamente

Supervisor commit

↓

B se vuelve activo

↓

A shutdown

Si B falla:

A permanece activo.

No se implementa Supervisor en 1.0.

DeviceBus ownership:

Cada CompositionRuntime crea
exactamente un DeviceBus candidato.

Configura Policy antes de dispatch.

No es autoload.

No es singleton.

No se comparte entre runtimes candidatos.

Activation pipeline:

1. Preflight.

2. Crear DeviceBus.

3. Configurar Dispatch Policy.

4. Resolver dependencies por Entry.

5. Crear RuntimeConstructionRequest.

6. Build de todos los Handles.

7. Attach de todos los Handles.

8. Bind de todas las Directives.

9. Initialize de todos los Handles.

10. set_ready de todos los Handles.

11. start de todos los Handles.

12. Commit ACTIVE.

Phase barriers:

Todos construidos antes de attach.

Todos attached antes de bind.

Toda comunicación enlazada
antes de initialize.

Todos initialized antes de ready.

Todos ready antes de start.

Todos started antes de ACTIVE.

Factory resolution:

Por Entry:

- Key exacta;

- Descriptor exacto;

- factory Object viva;

- misma Registry explícita;

- no fallback.

Preflight verifica que Registry
satisface todas las Entries
y que Specs coinciden.

Dependency resolution:

Por cada RuntimeDependencySpec:

- consultar availability;

- obtener Object;

- validar instance;

- crear Binding con Ownership de Spec.

No se permiten dependencies extra
porque Runtime itera Specs del Plan.

BORROWED:

Resolver conserva ownership.

TRANSFERRED:

Transferencia comienza al invocar
factory.build(request).

Build failure:

Factory limpia recursos locales
y TRANSFERRED del request actual.

Runtime no ejecuta segundo cleanup
del request fallido.

Handles anteriores:

Runtime ejecuta release inverso.

Attach failure:

RuntimeHost revierte attach parcial
del Handle actual.

Runtime ejecuta:

- detach anteriores inverso;

- release Handles inverso.

Bind failure:

Binder revierte bind parcial actual
por contrato o devuelve error.

Runtime ejecuta:

- unbind anteriores inverso;

- detach inverso;

- release inverso.

Lifecycle failure:

Si initialize actual falla:

- shutdown best effort del Handle actual;

- shutdown de Handles inicializados anteriores en orden inverso.

Si ready o start fallan:

- shutdown de todos los Handles initialized en orden inverso.

Después:

- unbind inverso;

- detach inverso;

- release inverso.

Rollback continúa aunque
una operación de cleanup falle.

Todos los Issues se agregan.

El simulador no pierde control
por un fallo de cleanup.

Shutdown activo:

1. shutdown reverse order.

2. unbind reverse order.

3. detach reverse order.

4. release reverse order.

5. DeviceBus.clear().

6. State SHUTDOWN si cleanup completo.

Si cleanup reporta errores:

State FAILED.
