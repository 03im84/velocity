Activation pipeline implementado:

1. Validar State CREATED.

2. Validar Plan.

3. Aplicar Hardware gate.

4. Validar Registry.

5. Validar collaborator behaviors.

6. Verificar Keys y Specs exactas.

7. Resolver Dependency Values declarados.

8. Crear DeviceBus candidato.

9. Configurar Dispatch Policy.

10. Crear RuntimeDependencyBindings.

11. Crear RuntimeConstructionRequests.

12. Build All.

13. Attach All.

14. Bind All Communication.

15. Initialize All.

16. Ready All.

17. Start All.

18. Commit ACTIVE.

Invariante:

No se exponen Plan, Bus o Handles parciales.

Commit ACTIVE ocurre únicamente
después de completar todas las fases.

Dependency resolution:

Runtime itera exclusivamente
RuntimeDependencySpecs del Plan.

Por Spec:

has_value(device_id, dependency_id)

+

get_value(device_id, dependency_id)

+

Spec Ownership

↓

RuntimeDependencyBinding

BORROWED conserva owner original.

TRANSFERRED entra a la transacción
durante factory.build(request).

Rollback implementado:

1. shutdown de initialized Handles
   en orden inverso.

2. unbind de Directives confirmadas
   en orden inverso.

3. detach de Handles confirmados
   en orden inverso.

4. release de Handles construidos
   en orden inverso.

5. DeviceBus.clear().

Initialize parcial:

El Handle actual se registra
antes de invocar initialize.

Si initialize falla después
de producir efectos parciales,
rollback incluye ese Handle
primero en shutdown best effort.

Cleanup best effort:

Un error no detiene
las operaciones restantes.

Todos los Issues se agregan
al Operation Result original.

Shutdown activo:

ACTIVE

→ SHUTTING_DOWN

→ cleanup inverso

→ SHUTDOWN si Report válido

o

→ FAILED si cleanup reporta error.
